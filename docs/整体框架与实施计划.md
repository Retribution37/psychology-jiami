## 1. 一句话定位

**本地 1.5B 小模型负责"看懂并抽象"隐私，云端大模型负责"分析"，两者通过一次受控回询协作；所有替换可逆、可审计，且云端请求中不出现任何真名、地址、账号。**

答辩时的四个贡献点，按这个顺序讲：

1. **关系型去标识化**：不是把"王浩"简单换成"人物A"，而是同时告诉云端"人物A 是来访者的同桌"。原文只写真名、没写关系时，云端仍然拿得到临床所需的上下文。
2. **回询–披露协议**：云端信息不足时可以提问，本地按最小披露策略决定"给抽象属性"还是"拒绝"，而不是把整篇档案再发一遍。
3. **三层评测**：泄漏率 + 重识别攻击 + 效用对照，回答"隐私保住了，分析质量掉了多少"。
4. **1.5B 微调 + llama.cpp**：证明窄任务上小模型够用，且本地部署可控。

同时要在报告里主动说明：**这里的"加密"是去标识化/伪名化，不是密码学加密**。云端必须读懂占位符才能维持上下文；真正的密码学加密会让大模型无法分析。这个区分写清楚是加分项。

## 2. 威胁模型

### 2.1 保护对象

- 直接标识符：真实姓名、昵称、具体学校/单位、家庭住址、电话、微信/QQ、身份证、学号、邮箱。
- 准标识符：年龄、年级、日期、罕见事件描述。它们单独不识别，组合起来可能重识别。

### 2.2 对手

- 云端服务商及其日志、运维人员。
- 传输链路窃听者。
- 本地映射表泄露（设备丢失、误发 CSV）。
- 恶意或被诱导的云端模型：通过回询问题套取身份。

### 2.3 明确保证

- 发往云端的请求体（文本 + legend + 回询答复）中**不出现**映射表中的任何真名、别名、地址、账号、note。
- 映射表只存在本地（浏览器内存 / 本地进程），不上传、不落盘（可选加密落盘）。
- 回译只在本地进行；云端只看到占位符。
- 小模型失败时**失败关闭**：返回错误，绝不降级发送原文。

### 2.4 明确不保证

- 不保证密码学意义上的密文。
- 不保证准标识符完全消除；用重识别攻击量化残余风险，并在报告里讨论。
- 不防护本地设备被完全控制、屏幕翻拍、治疗师主动泄露。
- 不防护 docx 页眉/页脚/批注/图片中的信息（见 6.5，至少要做到警告）。

## 3. 系统架构

```text
┌────────────────── 浏览器（映射表只在这里） ──────────────────┐
│ 上传 docx │ 原文/脱敏左右对照 │ 协议时间线 │ 还原报告 │ 云端可见内容 │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP（localhost）
┌───────────────────────────▼─────────────────────────────────┐
│ FastAPI（无状态、不落盘）                                     │
│                                                              │
│  1) docx_io：.docx → 纯文本                                   │
│                                                              │
│  2) 本地隐私层                                                │
│     llama.cpp + Qwen2.5-1.5B(LoRA) → 实体 JSON                │
│     代码校验 → 逐字替换 → 映射表（vault）                     │
│     泄漏扫描：别名精确匹配 + 正则 + 独立 NER                  │
│     不通过 → 拒绝发送，前端标红                               │
│                                                              │
│  3) 协议编排                                                  │
│     第一轮 → DeepSeek → 报告 + 结构化信息缺口                 │
│     策略引擎（规则表，非模型）→ 只放行抽象属性/拒绝           │
│     第二轮 → DeepSeek → 最终报告                              │
│                                                              │
│  4) 本地回译：占位符 → 真名                                   │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只发：脱敏文本 + legend + 抽象答复
                            ▼
                      DeepSeek API（云端）
```

### 3.1 两条链路

- **基线（Pipeline）**：脱敏 → 云端一次分析 → 本地回译。现有代码就是这条，保留作对照组。
- **提出方法（Protocol）**：脱敏 → 第一轮分析 + 缺口 → 本地策略披露 → 第二轮分析 → 回译。

两条链路共用同一套脱敏、映射、泄漏扫描和回译代码，保证实验只改变"协同协议"这一个变量。

## 4. 数据契约 v2（小模型输出）

### 4.1 输出格式

严格 JSON，不要 Markdown 代码块，不要解释文字：

```json
{
  "entities": [
    {
      "placeholder": "人物A",
      "category": "人物",
      "relation": "同桌",
      "aliases": ["王浩", "小王"],
      "note": "同桌，坐在来访者后排"
    }
  ]
}
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `placeholder` | 替换后的代称 | `来访者` 或 `人物X/地点X/账号X`，同一实体全局唯一 |
| `category` | 类别 | 只能是 `人物` / `地点` / `账号` |
| `relation` | 给云端的安全属性 | 必须来自 4.2 的词表；不确定就填空字符串；**绝不能写真实姓名/单位名** |
| `aliases` | 该实体在原文里的所有写法 | 必须逐字出现；代码会 `text.count()`，找不到就丢弃 |
| `note` | 本地备注 | 可以含真名；**永远不发给云端** |

### 4.2 受控词表

| 类别 | 允许值 |
|---|---|
| 人物关系 | 本人、父亲、母亲、父母、子女、兄弟姐妹、其他亲属、配偶、恋人、朋友、同学、同桌、室友、同事、老师、班主任、邻居、医生、其他 |
| 地点类型 | 学校、家庭住址、医院、单位、常去地点、其他 |
| 账号类型 | 电话、微信、QQ、邮箱、身份证、学号、银行卡、其他 |

`relation` 是唯一会随 legend 发给云端的语义属性；`note` 不出本地。

### 4.3 硬规则

1. 只有三类：人物 / 地点 / 账号。日期、年龄、年级、症状、诊断、事件、情绪都不算实体。
2. 同一实体的所有写法合并成一个对象、一个占位符。
3. 占位符按类别编号：人物A、人物B、地点A、地点B、账号A……
4. 患者本人固定叫 `来访者`，不编号、不进人物序列。
5. `aliases` 必须逐字出现在原文，不能改写、不能补全。
6. `relation` 只能从 4.2 词表选；写错/编造会导致该字段被清空（实体保留，隐私优先）。
7. `note` 可以含真名，但永远不参与替换、不发给云端。
8. 没有可脱敏内容时输出 `{"entities":[]}`，不要硬凑。
9. **不要改写正文**。只输出清单，替换由代码做。

### 4.4 示例

输入：

```text
来访者小明，男，16 岁，实验中学高二学生。近一个月因同桌王浩的言语嘲讽情绪低落。
母亲李梅反映其夜间失眠，联系电话 13800138000。
家庭住址：阳光小区3栋502。
```

输出：

```json
{"entities":[
  {"placeholder":"来访者","category":"人物","relation":"本人","aliases":["小明"],"note":"患者本人"},
  {"placeholder":"人物A","category":"人物","relation":"同桌","aliases":["王浩"],"note":"同桌"},
  {"placeholder":"人物B","category":"人物","relation":"母亲","aliases":["李梅"],"note":"母亲"},
  {"placeholder":"地点A","category":"地点","relation":"学校","aliases":["实验中学"],"note":""},
  {"placeholder":"地点B","category":"地点","relation":"家庭住址","aliases":["阳光小区3栋502"],"note":"家庭住址"},
  {"placeholder":"账号A","category":"账号","relation":"电话","aliases":["13800138000"],"note":"电话"}
]}
```

替换后：

```text
来访者，男，16 岁，地点A高二学生。近一个月因同桌人物A的言语嘲讽情绪低落。
母亲人物B反映其夜间失眠，联系电话 账号A。
家庭住址：地点B。
```

发给云端的 legend：

```text
===== 脱敏说明 =====
- 来访者（人物代称，关系：本人）
- 人物A（人物代称，关系：同桌）
- 人物B（人物代称，关系：母亲）
- 地点A（地点代称，类型：学校）
- 地点B（地点代称，类型：家庭住址）
- 账号A（账号代称，类型：电话）
```

注意：原文恰好写了"同桌""母亲"时，关系会重复出现在正文和 legend 里，这是刻意的冗余；原文只写"王浩在班里散布……"时，legend 仍然告诉云端"人物A 是同桌"。这就是关系属性要解决的问题。

### 4.5 代码校验（anonymize.py 要补的）

- 别名不在原文 → 丢弃该别名；整个实体没有有效别名 → 丢弃实体。
- `relation` 不在词表 → 清空，**实体保留**（不能因为关系写错就漏脱敏）。
- 同一 placeholder 多条 → 合并；类别冲突 → 保留第一条并记日志。
- 单字中文别名 → 丢弃（账号类除外），防止"王""明"把全文替换坏。
- 别名是占位符的子串/停用词 → 丢弃，防止破坏占位符与正文。
- 替换按别名长度降序，长串优先，避免"张三"吃掉"张三丰"。

## 5. 协同协议

### 5.1 时序

```text
本地                          云端
 │  ① 脱敏文本 + legend         │
 │ ───────────────────────────▶ │
 │                              │ 第一轮：分析 + 找信息缺口
 │  ② {report_md, gaps[]}       │
 │ ◀─────────────────────────── │
 │                              │
 │  ③ 策略引擎逐条裁决           │
 │     - 关系类 → 给受控属性     │
 │     - 身份类 → 拒绝           │
 │     - 未知类 → 默认拒绝       │
 │                              │
 │  ④ 脱敏文本 + legend + 抽象答复│
 │ ───────────────────────────▶ │
 │                              │ 第二轮：出最终报告
 │  ⑤ 最终报告（占位符）         │
 │ ◀─────────────────────────── │
 │  ⑥ 本地回译 → 展示两个版本    │
```

### 5.2 缺口 schema

云端第一轮返回严格 JSON：

```json
{
  "report_md": "## 一、个案概况与主诉\n……",
  "gaps": [
    {
      "id": "g1",
      "type": "relationship",
      "target": "人物A",
      "question": "人物A与来访者是什么关系？这会影响对冲突性质的理解。"
    }
  ]
}
```

`type` 只能是：`relationship` / `frequency` / `duration` / `identity` / `clinical_detail` / `other`。`target` 必须是 legend 里出现过的占位符；不合法就丢弃该缺口。

### 5.3 披露策略表（规则引擎，不是模型）

| gap type | 云端想问的 | 本地裁决 |
|---|---|---|
| `relationship` | 人物A与来访者关系 | 若映射表有 `relation` → 回答该属性；否则"不便披露" |
| `frequency` / `duration` | 冲突频率/持续时间 | 若脱敏文本里已有 → 原样引用；没有 → 拒绝，不编造 |
| `identity` | 真实姓名/学校/地址 | **一律拒绝** |
| `clinical_detail` | 是否有自伤史/诊断 | 若文本里已有 → 引用；没有 → 拒绝，不编造 |
| `other` / 未知 | 任何其他问题 | 默认拒绝 |

关键设计：**披露决策由确定性代码做，不由 1.5B 模型做**。小模型只负责抽取和关系标注；安全决策必须可审计、可复现。

### 5.4 拒绝与审计

- 每条缺口记录：`{gap_id, type, target, decision: allow|deny|abstract, reason}`。
- 前端时间线展示"云端问了什么 / 本地给了什么 / 为什么拒绝"。
- 演示一个身份套取问题（例如云端问"人物A 是不是叫王浩？"）被拒绝，这是协议的价值证明。
- 第二轮 prompt 要求：在报告第五节"信息缺口"里写明哪些问题被本地拒绝，不得反推真实身份。

### 5.5 失败与降级

- 第一轮 JSON 不合法 → 重试一次（修复提示）；仍失败 → 降级到单向管道（只发脱敏文本），**绝不发原文**。
- 本地小模型失败 → 502，失败关闭。
- llama.cpp 不可达 → 健康徽标变红，禁用"加密"按钮；不允许改用云端模型做抽取（那会直接泄露）。
- 回询轮数上限 1 轮；第二轮不再提问，避免无限协商。

## 6. 隐私护栏

### 6.1 发送前扫描（新增 `privacy_guard.py`）

1. **别名精确扫描**：映射表里每个 `original` 和 `aliases` 都不能出现在脱敏文本里。
2. **正则扫描**：手机号、身份证、邮箱、QQ、银行卡、微信号格式。
3. **独立 NER**：用 GLiNER-multi / HanLP 对脱敏文本再抽一遍人名/地点/机构；命中项若不在占位符集合里，标为风险（警告，不直接阻断，避免误杀）。
4. **占位符完整性**：文本里出现的占位符必须在映射表中；未知占位符要警告。

### 6.2 服务端强制（修掉"手动编辑泄密"）

`/api/analyze` 在调用云端前，用映射表把 6.1 的 1、2 两项再跑一遍。命中则返回 400，提示"发现疑似未脱敏内容：人物A 的原名仍在文本中"——**不要回显真名**。

这条把隐私保证从"靠前端自觉"变成"系统强制"，也是演示时最有说服力的一幕：故意把真名改回去，点分析，被系统拦下。

### 6.3 别名 sanity

- 单字中文别名丢弃（账号除外）。
- 别名是占位符子串（"人物""地点""来访者"）或停用词 → 丢弃。
- 别名长度、出现次数、是否包含数字/字母，记入映射表，供人工复核。

### 6.4 映射表（vault）

- 默认只在浏览器内存 + 本地进程内存；刷新即清空，不落盘。
- 可选：落盘时用 Fernet（口令派生密钥）加密，密钥不进代码库。
- CSV 导出会含真名，前端要明确提示"这是敏感文件，仅限本机"。
- 日志只记占位符数量、token 数、时延，不记正文、不记映射。

### 6.5 docx 边界

- 当前只处理正文段落 + 表格；页眉/页脚/批注/修订/图片不处理。
- 上传时检测是否存在页眉/页脚/批注，存在就警告："这些位置不会被脱敏，请先清理。"
- `.doc` 不支持；前端提示另存为 `.docx`。

### 6.6 准标识符

- 日期、年龄、年级不在当前契约里；这是有意的取舍（临床分析需要）。
- 在威胁模型里明确写出来，并用重识别攻击量化风险。
- 可选实验开关：日期粗化到"月份/季节"，年龄粗化到"年龄段"；作为消融项，不改主线契约。

## 7. 小模型：Qwen2.5-1.5B 微调 + llama.cpp

### 7.1 选型

- 主模型：**Qwen2.5-1.5B-Instruct**。窄任务、中文、1.5B 足够；8GB 显存训练/推理都宽松；GGUF 生态成熟。
- 备选：Qwen3-1.7B（更新，但默认可能带思考模式，JSON 输出要显式关闭思考）。
- 对照：base 1.5B（不微调）、Qwen2.5-7B-Instruct（零样本），用来证明"微调 1.5B 够用"。

### 7.2 训练数据

- 300–800 条合成档案；30 篇独立测试集，绝不进训练。
- 每条覆盖 1–3 个难点：别名合并、泛称不替换、机构名 vs 地名、号码格式、空输出、关系标注、长文档。
- 格式对齐线上调用：

```json
{"messages":[
  {"role":"system","content":"<与 app/prompts.py 完全一致的 EXTRACT_SYSTEM>"},
  {"role":"user","content":"<档案纯文本>"},
  {"role":"assistant","content":"<金标 JSON，压缩成一行，不带代码块>"}
]}
```

- 金标 JSON 必须包含 `relation` 字段；**契约先冻结，再造数据**，否则数据白造。
- 生成方式：大模型按模板生成 + 固定假名/假地址池注入 + 人工核验；不要用真实档案。

### 7.3 训练

- LoRA（fp16，不用 QLoRA）：r=16、alpha=32、lr=2e-4、3 epochs、batch=1、梯度累积 8、seq_len=2048、temperature 训练用默认。
- 工具：LLaMA-Factory（Windows 可用，支持 Qwen2.5 + LoRA + 导出 GGUF）。
- 环境：RTX 5060 是 Blackwell，PyTorch 需要 cu128 及以上；装不上或训练报错就把训练放云 GPU（AutoDL/Colab），数据是合成的，不涉及隐私；训练完把合并后的 HF 权重拿回本地转 GGUF。
- 训练目标顺序：先保 JSON 格式与硬规则，再提召回。格式坏 = 整条链路失败。

### 7.4 导出与 llama.cpp 服务

```text
LoRA 合并 → HF 权重
  → llama.cpp/convert_hf_to_gguf.py
  → Q4_K_M 或 Q5_K_M
  → llama-server -m model.gguf -ngl 99 -c 4096 --port 8080
```

- 用 llama.cpp 的 GBNF / JSON schema 约束输出结构（具体走 `/completion` 的 grammar 字段或 OpenAI 兼容端的 response_format，以安装的版本为准）。结构由解码器保证，语义规则（别名逐字、词表、编号）仍由代码校验。
- temperature=0；`--ctx-size 4096` 起步，长文档先截断/分块，见 12 节局限。
- 健康检查打 llama.cpp 的 `/health` 或 `/v1/models`，不要只 ping 端口。

### 7.5 代码改动

- `config.py`：`OLLAMA_*` → `LOCAL_*`；新增 `LOCAL_BACKEND=llamacpp|ollama`，Ollama 保留为兜底。
- `llm.py`：新增 llama.cpp 客户端（OpenAI 兼容 `/v1/chat/completions`），失败重试一次；Ollama 路径保留。
- `.env.example` / `README.md`：同步默认值、启动命令、模型名。
- 前端徽标：显示"小模型：llamacpp / 模型名 / 是否就绪"。

### 7.6 微调评测

同一套 30 篇金标，比较：

| 模型 | JSON 合法率 | 契约违规率 | 实体召回 | 过替换率 | 关系准确率 | 延迟 |
|---|---|---|---|---|---|---|
| base Qwen2.5-1.5B | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| **微调 Qwen2.5-1.5B** | 目标 100% | <5% | ≥90% | <5% | ≥80% | 待测 |
| Qwen2.5-7B 零样本 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |

## 8. 实验设计（三层）

### 8.1 数据

- 30 篇合成测试档案，人工核验；每篇 5–15 个金标实体。
- 覆盖：无隐私、大量别名、纯号码、机构名、泛称干扰、关系缺失（原文只写真名）、长文档。
- 所有姓名/学校/地址/号码均为虚构；不使用任何真实档案。
- 训练集与测试集严格分离；测试集在契约冻结后不再改动。

### 8.2 条件

| 条件 | 说明 | 作用 |
|---|---|---|
| A. 原文直发 | 原始档案直接给 DeepSeek | 效用上界、隐私下界（泄漏率 100%） |
| B. 单向管道 | 现有系统：脱敏 → 云端 → 回译 | 基线 |
| C. 回询协议 | 脱敏 → 第一轮 → 策略披露 → 第二轮 → 回译 | 提出方法 |
| D. 消融 | C 去掉关系属性；C 去掉泄漏扫描；base vs 微调；1.5B vs 7B | 证明每个部件有用 |

### 8.3 指标

| 层 | 指标 | 定义 |
|---|---|---|
| 抽取 | JSON 合法率 | 能 `json.loads` 的比例 |
| 抽取 | 契约违规率 | 类别错/别名不存在/同人双占位/关系不在词表 |
| 抽取 | 实体召回 | 命中金标实体数 / 金标总数 |
| 抽取 | 过替换率 | 泛称或非隐私被替换的比例 |
| 抽取 | 关系准确率 | `relation` 与金标一致的比例 |
| 隐私 | 直发泄漏率 | 云端请求中出现金标 PII 的比例（目标 0） |
| 隐私 | 脱敏残留率 | 脱敏后文本中金标 PII 残留比例（独立 NER + 精确匹配 + 人工抽查） |
| 隐私 | 重识别准确率 | 攻击模型从 10 份候选档案中匹配真实身份，top-1 准确率 vs 随机 10% |
| 隐私 | 拒绝正确率 | 身份类缺口被拒绝的比例（目标 100%） |
| 效用 | 报告 rubric 分 | 五节结构 + 临床要点覆盖，0–10 分 |
| 效用 | 关键点覆盖率 | 金标临床要点被报告覆盖的比例 |
| 成本 | 轮数 / token / 时延 | 本地推理时延、云端时延、总 token |

### 8.4 重识别攻击

- 每篇测试档案构造 10 份候选画像（1 真 + 9 假，年龄/学校/事件模式相近）。
- 攻击模型（DeepSeek）拿到脱敏文本 + 10 份候选（含姓名/学校/地址），选最匹配的一份。
- 记录 top-1 准确率；随机基线 10%。条件 B、C 都跑。
- 若准确率明显高于随机，说明准标识符在泄漏；报告里列出驱动特征（年龄、日期、罕见事件、关系词）。
- 另做"属性推断"：让攻击模型直接从脱敏文本猜真实姓名/学校/地址，记录精确/部分匹配率。由于数据是虚构的，攻击模型没有外部知识，候选池匹配才是主指标。

### 8.5 预期结果（假设，不是承诺）

- A：效用最高，泄漏率 100%。
- B：直接泄漏 0，但关系缺失案例的效用下降。
- C：效用接近 A（比 B 高 10–15%），直接泄漏 0，多一轮调用。
- 微调 1.5B：JSON 合法率 100%（grammar 保证）、召回 ≥90%、关系准确率 ≥80%，接近 7B 零样本；base 1.5B 明显更差。

### 8.6 成本与伦理

- DeepSeek 调用量估算：30 篇 × 3 条件 × 2 轮 + 攻击 + 评分 ≈ 200–400 次；先跑 5 篇小规模验证，再全量。
- 全部使用合成数据；演示用虚构案例；不上传任何真实心理档案。
- 报告里写明数据合成方法与人工核验流程。

## 12. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| Blackwell + PyTorch 环境装不上 | 微调阻塞 | 训练放云 GPU；本地只做 GGUF 推理；数据是合成的 |

| 演示现场网络/模型故障 | Demo 翻车 | 录屏备份 + 离线 smoke + 预生成结果 |
| 准标识符被攻击成功 | 隐私结论被质疑 | 如实报告重识别准确率；讨论日期粗化等缓解 |
